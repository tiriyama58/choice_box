# 敵対レビュー

引数 `$ARGUMENTS` は、レビュー対象ファイルのパスである。1ファイルだけを受け取る。

計画・設計の敵対的レビューを行い、結果をHTMLレポートに書く。対象ファイルの実装変更、それ以外のファイル変更、デプロイはしない。書いてよいファイルは、下記のレポート1つだけである。

## 始める前に読む

次を読み、本文の指示より各ファイルの現行の定めを優先する。

- `.cursor/rules/adversarial-review.mdc`
- `.cursor/rules/report-design.mdc`
- `reports/review-design-verification.html`（見た目の原本）
- yomiyasu スキル（`~/.cursor/skills/yomiyasu/SKILL.md`）

引数が空、またはファイルを読めないときは、理由を伝えて止める。ディレクトリを渡されたときも、対象ファイルを尋ねて止める。

対象ファイルのほかに、判断に必要な制約と呼び出し関係だけを読む。`AGENTS.md`、対象が依存する型、対象を呼ぶ箇所が該当する。レビュー範囲を広げて別機能まで調べない。

## レビュー

`.cursor/rules/adversarial-review.mdc` の原則、手順、指摘の分類、制約、出力の6項目に従う。

対象が計画や設計の文書なら、その計画をレビューする。対象がコードなら、そのコードに現れている設計判断をレビューする。行単位の体裁指摘や、指摘数を増やすための列挙はしない。問題がなければ、問題なしとする。

各指摘は次のどれか一つに分類し、判断理由を付ける。

| 分類 | レポートのバッジ | `data-severity` |
|---|---|---|
| 必ず修正 | Critical | `critical` |
| 修正を推奨 | Warning | `warning` |
| 許容可能 | Info | `info` |

Suggestion バッジは使わない。許容可能な指摘は Info とし、絞り込みの「Info / Suggestion」に含める。

指摘ごとに、根拠、発生条件、影響範囲、重大度、最小限の改善案を示す。確認済みの事実、推測、未確認事項を混ぜない。根拠のない問題や、未確認の仕様を事実として書かない。明示された制約は、根拠なく変えたり緩めたりしない。

## 日本語

レポートに書く日本語は、保存前に yomiyasu の手順で推敲する。コード引用、ファイル名、行番号、識別子、数値は原文のまま残す。

- 文書の種類は business（社内のレビュー報告）。立場は説明。読み手は informed。
- 推敲の確認欄はHTMLに入れない。チャットの返答に、yomiyasu の出力フォーマットで残す。
- スキルの検査スクリプトを、スキルの定めどおり実行する。実行できないときは、その旨を確認の記録に書く。

## レポート

見た目は `reports/review-design-verification.html` に合わせる。CSSと絞り込みのJavaScriptは原本から写し、単一HTMLに含める。外部フォント、外部CSS、外部ライブラリは使わない。色、幅、フォント、カード、バッジ、絞り込みは `.cursor/rules/report-design.mdc` に従う。

保存先のファイル名は `.cursor/rules/report-design.mdc` のファイル名の定めに従う。種類は `adversarial-review` とする。例: `src/lib/history.ts` を2026年10月18日にレビューするなら `reports/adversarial-review-src-lib-history-20261018.html`。

構成は次のとおりにする。

- ヘッダーのプロジェクト名は Choice Box。レビュー実施日時は、実行時点の日本時間を「2026年10月18日 7:41」の形で書く。
- 総指摘件数と、Critical、Warning、Info / Suggestion の内訳を置く。Info / Suggestion の件数は Info の件数である。
- リード文に総合評価を書く。
- 指摘はカードにする。各カードに、バッジ、ファイル名と行番号、概要、詳細、問題のあるコード、改善後の提案、修正理由を置く。詳細には、分類と判断理由、根拠、発生条件、影響範囲、事実か推測か未確認かの区別を含める。
- カードの後に、同じカードの体裁で「推奨する修正後の計画」と「未確認事項と追加調査が必要な事項」を置く。この2つは絞り込みの対象外にする。
- 指摘がゼロのときは、件数を0にし、総合評価で問題なしと書く。空の一覧には、原本と同じ空表示を使う。

コードはHTMLエスケープする。行が長い場合は折り返す。アニメーションや装飾は足さない。

## 返答

チャットでは、総合評価、指摘件数、レポートのパスを先に書く。続けて yomiyasu の確認欄を書く。対象ファイルは変更していないことと、未確認事項がある場合はその要点を添える。
